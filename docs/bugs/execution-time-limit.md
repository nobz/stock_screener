# 「起動時間の最大値を超えました」で銘柄データ更新が止まる（2026-11-22）

## 症状

キャッシュクリア直後に「銘柄データ更新」を実行すると、途中で GAS が「起動時間の最大値を超えました」と表示して止まる。`pickup` は更新されない。

## 原因

GAS の1回の実行は6分まで。業種一覧のページ取得（全業種）に加えて、候補ごとに時系列ページ（出来高）と財務ページ（配当チェック）を1件ずつ取得するようになり、キャッシュが空の初回は合計で6分を超えた。財務ページの取得を加えたことが直接のきっかけ。

## 対処

- `runPickup` に時間予算（`TIME_BUDGET_MS` = 270秒）を設けた。ページ取得の前と、出来高・財務の1銘柄ごとに経過時間を確認し、超えたら例外 `TimeBudgetExceeded` で打ち切って `{ done: false }` を返す
- 打ち切った回は `pickup` と `history` を書き換えない。取得済みのページ・出来高・財務はキャッシュに残る
- サイドバー（`progress.html`）は `done: false` を受け取ると `runPickup` をもう一度呼ぶ。新しい実行なので6分の枠がリセットされ、キャッシュ済みの分は飛ばして続きから進む。無限ループを避けるため最大8回で打ち切る
- テスト「時間予算を超えたら打ち切って続きを返し、再実行でキャッシュから完了する」で確認

## 追加の症状: NetworkError: HTTP 0（同日）

- 上記の対処後、サイドバーに「エラーで止まりました: NetworkError: 次の原因のために接続できませんでした: HTTP 0」と出て止まった（経過437秒）
- 原因（推測）: スクリプトのエラーではなく、サイドバーと `google.script.run` の通信切断。1回の呼び出しが4分半近く続いたため接続が切れたと考えられる。CLI の `clasp logs` は GCP プロジェクト未設定で使えず、サーバー側ログでの裏付けは取れていない
- 対処:
  - 時間予算を270秒から150秒に縮め、短い呼び出しを回数多く行う（最大20回）
  - サイドバーは NetworkError を受けたら10秒待って最大3回まで再試行する。進み具合はキャッシュにあるので安全
  - 通信が切れてもサーバー側の実行は続いている場合があるため、`LockService` で `runPickup` を同時に1つだけ動かす。ロックが取れない呼び出しは `{ busy: true }` を返し、サイドバーは10秒ごとに待つ（最大30回）。`pickup` と `history` の二重書き込みを防ぐ

## 追加の症状: 続き実行が8回を超えても終わらない（同日）

- 原因: 出来高と財務のページを1銘柄ずつ順番に取得していた。第1段階の通過が約500件あると、約1,000回の取得（1回およそ1秒）になる
- 対処: `collectByTicker` でキャッシュは `getAll` でまとめて読み、足りない分だけ `UrlFetchApp.fetchAll` で10件ずつ同時に取得するようにした。`fetchAll` は1件でも通信例外があると全体が失敗するので、そのバッチだけ1件ずつ取り直す
- 同時取得数（`FETCH_BATCH_SIZE`）を上げすぎると株探側で弾かれるおそれがある（推測）。HTTP 403/429 がログに増えたら下げる

## 追加の症状: 150秒で区切ったのに続きが呼ばれない（2026-11-24）

- ログは「適用設定」「業種リストを固定値から取得: 33件」のあと、経過150秒で「一旦区切りました」となり、2回目の「適用設定」が出なかった。サーバー側は `{ done: false }` を返すところまで進んでおり、続きを呼ぶのはサイドバー側の役目
- 原因（推定）: 150秒続いた `google.script.run` の応答がサイドバーへ届かず失敗として落ちたうえ、その失敗文が再試行の条件（`NetworkError` / `HTTP 0` を含むこと）に合わず、本来は通信切断なのに即「エラーで止まりました」になっていた。CLI から実環境ログを引けないため、失敗文そのものの裏付けは取れていない
- 対処:
  - 時間予算を150秒から90秒に縮め、区切りの応答が届くうちに1回を終えるようにした。最大20回でも約30分で、業種ページのキャッシュ（1時間）の範囲内
  - サイドバーは失敗文の文面によらず、10秒待って最大5回まで再接続するようにした。再呼び出しはキャッシュの続きから進み、`LockService` で二重実行にならないため安全。上限を超えたら元のエラーを表示して止める
  - テスト「サイドバーは NetworkError でない失敗でも再接続し、区切りの続きを呼ぶ」で、文面の違う失敗→再接続→区切り→完了の流れを確認。旧条件に戻すとこのテストが落ちることも確認済み

## 追加の症状: 手動で再実行すると完走するが、自動では続かない（2026-11-25）

- 90秒化とサイドバーの再接続を入れたあとも、自動の続きは動かず、手動でもう一度実行するとキャッシュから完走した。サーバー側の再開（キャッシュ）自体は効いており、届いていないのはサイドバーからの呼び直しだけと切り分けた
- 対処: 続きの実行をサイドバーだけに頼るのをやめ、区切りのたびにサーバー側でも時間トリガー（1分後、`continuePickupFromTrigger`）を1つだけ予約するようにした
  - トリガー実行時はアクティブなスプレッドシートが無いため、通常実行時にスプレッドシート ID と実行モード（通常／キャッシュ再判定）をスクリプトプロパティへ残し、トリガーは `SpreadsheetApp.openById` で開く
  - サイドバーとトリガーが競合しても `LockService` で片方だけが動く。トリガーが実行中（busy）に当たったら予約し直し、完走・本物のエラー時は予約を消す
  - トリガーの予約に失敗してもサイドバー側の継続は残る（例外はログだけに留める）
  - `runPickup` の入口と busy 返却にもログを足し、呼び直しが届いたかどうかを次回ログで追えるようにした
- テスト「時間予算で区切ったら継続トリガーを1つだけ予約し、トリガーから完走して予約が消える」で確認

## 再発防止・注意

- 続きの実行はキャッシュに依存する。業種ページのキャッシュは1時間なので、全体が1時間以内に終わる前提。20回×90秒は最大約30分で収まる
- スクリプトエディタから `create_pickup_stocks` を直接実行した場合も、区切りのたびに継続トリガーが予約され、1分後からサーバー側で続きが進む。戻り値が `done: false` でも手動の再実行は不要（急ぐ場合は再実行してもロックで二重実行にならない）
- 取得対象を増やすときは、キャッシュが空の初回の所要時間を見積もる。経過時間はログ「ここまでの経過時間」に出る
- 根本対応だった先送り項目（[deferred/screener-improvements.md](../deferred/screener-improvements.md) の4番「中断・再開の仕組み」）は、この対処で解消した
